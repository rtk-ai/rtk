# OpenCode Hooks

> Part of [`hooks/`](../README.md)

## Specifics

- TypeScript plugin (not a shell hook)
- Supports **OpenCode 2.0** (`execute.before` via `{ id, setup }`) and **OpenCode 1.x >= 1.18.29** (`tool.execute.before`), the dual-shape default export [OpenCode's own V2 docs prescribe](https://opencode.ai/v2/docs/build/plugins)
- Requires OpenCode **1.18.29 or newer**, the floor OpenCode's V2 plugin docs give for this dual-shape export. With an older OpenCode, `rtk init -g --opencode` writes nothing and leaves an existing plugin alone, when it can read `opencode --version`
- Thin delegating shim: calls `rtk hook opencode` as a subprocess, and the Rust side is the single source of truth for rewrite rules
- The Rust side judges the command against OpenCode's own permission rules and answers `{}` whenever the rewrite would change the verdict those rules give — OpenCode evaluates the final command itself, so RTK never lifts a deny, silences an ask, or blocks an allow (#4195). Rules are read from root and project `opencode.json`/`.jsonc` in the order OpenCode resolves them: the legacy `permission` map first, then the 2.x `permissions` list, whatever order the file declares them. Every file's root rules load before any file's agent rules, so a project `allow` cannot outrank a global agent `ask`. 2.x list actions match as globs against `shell`, so `sh*` covers it; a list rule whose action only names `bash` does not count, because OpenCode ignores it there. A legacy map key the two generations read differently (`shell` and `sh*` apply only on 2.x, `b*` only on 1.x) makes rtk leave the command as typed, because it cannot tell which generation it is serving. Global rules come before project rules. An agent defined as a markdown file in `agents/` or `agent/`, under `~/.config/opencode/` or any `.opencode/` from the working directory up, whose frontmatter declares `permission:` or `permissions:`, is not parsed here, so no rewrite happens for that agent and OpenCode applies its own rules.
- Uses standard `node:child_process.execFile` (compatible with OpenCode CLI, OpenCode Desktop/Electron, and Windows; zero Bun/zx dependencies)
- Passes the command as a single argv element, never through a shell
- Resolves rtk in this order, skipping any directory named `rtk`: OpenCode's own `PATH` (`PATHEXT` on Windows), then `RTK_BIN` when it is an absolute path to a file named `rtk`, then `~/.cargo/bin`, `~/.local/bin` (`install.sh`'s default), `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` and, on Windows, `%LOCALAPPDATA%\cargo\bin` and `%ProgramFiles%\rtk`. The rewrite stays a bare `rtk …`, so OpenCode judges the same string `rtk hook opencode` judged; to make every `rtk` in it resolve, the plugin appends rtk's directory to the end of the spawned shell's `PATH` through OpenCode 2.x's `ctx.shell.hook("create.before")` and OpenCode 1.x's `shell.env` hook. Appending leaves every command that already resolves on `PATH` resolving to the same binary (the other programs in rtk's directory become reachable too), and changes nothing at all when rtk is already on `PATH`. That is also why an rtk on `PATH` comes before `RTK_BIN`: it is the one the shell runs, so it is the one that has to judge the command (#4462)
- Passes OpenCode 2.x's `event.agent` as `rtk hook opencode --agent <name>`, so an `agent.<name>.permission` ask or deny is judged against the agent that runs the command. OpenCode 1.x sends no agent field, so that path stays root-only
- Two separate off switches, both named `RTK_DISABLED`. The per-command form is `RTK_DISABLED=1 git status`, an env prefix inside the command string; the Rust rewrite engine handles that one and the plugin passes the string through untouched. The plugin also reads `RTK_DISABLED=1` from OpenCode's own process environment, which switches rewriting off for the whole session
- Mutates command in-place (`event.input.command` in v2, `output.args.command` in v1) if the answered rewrite differs from the original
- Compresses tool output after the fact through `rtk hook opencode-after`, in both shapes: 2.x `execute.after` (`event.result.content`) and 1.x `tool.execute.after` (`output.output`). Only a completed call is touched, only when every content block is text, and only when the replacement is strictly smaller in bytes. The payload on stdin carries `tool`, `args`, `output`, plus the metadata the hook already has: `status` (2.x), `metadata.exit`, `description` and `duration_ms` (from `metadata.durationMs`/`duration_ms`, or a `metadata.time` start/end pair). Missing fields simply omit, so facts conditions such as `exit_code` and `duration_ms` see what the host knows
- Asks for a versioned envelope (`"expect":{"envelope":1}` in the payload) and reads `{"v":1,"output":"<replacement>","append":"<note>"}` back: one object on stdout, `append` always present and empty when there is no note. `output` replaces the tool result; `append` is appended to it, never substituted, and carries the Read→Edit fidelity note plain text has no room for. The request flag is what keeps a binary upgrade without re-running `rtk init` safe: a plugin from before the envelope sends nothing and gets plain replacement text, and a binary from before it answers plain text regardless. A stdout that is not JSON, or whose `v` is not `1`, is read as the replacement text itself, so either version skew stays fail-open
- Registers the after hook only when the resolved pipeline has a `hook.after_tool.<subject>` rule that can actually fire — not disabled by an override, not inert because it uses a pro-edition key: one `rtk hook opencode-after --probe` call per session answers `{"v":1,"active":true|false}`, and an inactive pipeline spawns no process per tool call. A binary that does not know `--probe` (exit 2, or a non-JSON answer) is registered exactly as before, so version skew never turns compression off
- Hook calls time out on `RTK_OPENCODE_HOOK_TIMEOUT_MS` (default `15000`, which covers an 8 s classifier; clamped to 2^31-1 ms because a longer `setTimeout` fires immediately). The first kill prints one warning naming the variable, the child gets SIGKILL if it outlives SIGTERM by 2 s, and a slow rule never prints a line per tool call
- Each compression writes one `rtk gain` row labelled `rtk posthook <tool> <format>` (e.g. `rtk posthook shell term`), the same label the Claude Code transport writes, so the two transports' savings show up side by side
- Trusts the resolved `rtk` binary's stdout — the one on `PATH`, or `RTK_BIN` when no `rtk` is there. Anything that can substitute that binary can answer this transport, so protecting it is an install-level concern, out of scope here
- Any failure — non-zero exit, timeout, non-JSON stdout, missing binary — passes the command through unchanged
- Installed to `~/.config/opencode/plugins/rtk.ts` by `rtk init -g --opencode`
- Tests: `node --test hooks/opencode/rtk.test.mjs`
