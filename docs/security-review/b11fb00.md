## Executive Summary

Comprehensive multi-vector security audit of RTK (Rust Token Killer) at commit b11fb00. The codebase demonstrates strong security fundamentals -- parameterized SQL queries, safe command argument passing via `Command::arg()`, and graceful error handling with `anyhow`. Two fixable issues were identified and remediated: a UTF-8 byte-slicing panic in tee output truncation and an unescaped regex pattern interpolation. Several medium/low design-level observations are documented for defense-in-depth hardening.

### High (Should Fix)

#### FINDING-001: UTF-8 Byte-Slicing Panic in Tee Truncation
- **Category**: OWASP Input Validation / CWE-135 (Incorrect Calculation of Multi-Byte String Length)
- **CVSS Estimate**: 5.3 (Medium - Availability impact, no confidentiality/integrity)
- **File**: `src/tee.rs:122-127`
- **Description**: The `write_tee_file()` function truncates large outputs at `max_file_size` bytes using `&raw[..max_file_size]`. Since `raw` contains arbitrary command output (which may include multi-byte UTF-8 characters like emoji, CJK, or accented characters), slicing at a byte boundary that falls inside a multi-byte character causes a **panic at runtime** (`byte index N is not a char boundary`).
- **Impact**: Any command producing output with multi-byte UTF-8 near the 1MB truncation boundary causes RTK to crash. This is a denial-of-service vector -- a crafted git commit message, filename, or error message with strategic emoji placement could trigger it.
- **Recommendation**: Use `str::is_char_boundary()` to find the nearest valid boundary before slicing.
- **Financial/Infra Impact**: In CI/CD pipelines, an unexpected panic terminates the pipeline step. For financial systems, this could disrupt automated deployment or audit log collection processes. Crash = loss of the tee recovery file, reducing forensic capability.

#### FINDING-002: Unescaped Regex Pattern Interpolation in Summary
- **Category**: OWASP Input Validation / CWE-185 (Incorrect Regular Expression)
- **CVSS Estimate**: 3.7 (Low - currently safe callers, but API is unsafe by design)
- **File**: `src/summary.rs:292-297`
- **Description**: The `extract_number()` function interpolates its `after` parameter directly into a regex pattern via `format!(r"(\d+)\s*{}", after)` without escaping. While current callers only pass safe literal strings ("passed", "failed", "skipped", "ignored"), the function signature accepts arbitrary `&str`. If a future caller passes user-derived input or a string containing regex metacharacters (e.g., `"test()"`), it could cause regex compilation failure or unexpected matching behavior.
- **Impact**: Currently unexploitable due to safe callers. However, the unsafe API pattern is a latent vulnerability -- any future change that passes external data to this function would create an immediate injection vector.
- **Recommendation**: Apply `regex::escape()` to the `after` parameter before interpolation.
- **Financial/Infra Impact**: Low immediate risk. Pattern represents a defensive coding gap that could be exploited if the codebase evolves.

### Medium (Consider Fixing)

#### FINDING-003: Shell Execution via `sh -c` in Runner and Summary
- **Category**: OWASP OS Command Injection Defense
- **CVSS Estimate**: N/A (by design -- user provides the command intentionally)
- **Files**: `src/runner.rs:14-26,73-85`, `src/summary.rs:15-27`
- **Description**: The `run_err()`, `run_test()`, and `summary::run()` functions execute user-provided command strings via `sh -c` (Unix) or `cmd /C` (Windows). This enables full shell expansion including pipes, redirects, and command chaining (`;`, `&&`, `||`). While this is intentional (the user explicitly provides the command via `rtk err <cmd>` or `rtk test <cmd>`), it differs from the safe `Command::new().arg()` pattern used in all other modules.
- **Impact**: In automated contexts (CI/CD, scripts), if the command string originates from an untrusted source (config file, environment variable, webhook payload), shell injection is possible. The `runner.rs` and `summary.rs` modules are the ONLY modules in the codebase that use shell invocation.
- **Recommendation**: Document this as an intentional design choice. Consider adding a warning in `--verbose` mode when shell metacharacters are detected. For a future hardening pass, consider parsing the command string and using `Command::new().arg()` with explicit pipe support.
- **Status**: Accepted Risk -- by design for shell feature support.

#### FINDING-004: Unvalidated Environment Variable Paths
- **Category**: OWASP Input Validation / CWE-22 (Path Traversal)
- **CVSS Estimate**: 3.1 (Low - requires local environment manipulation)
- **Files**: `src/tee.rs:37-38`, `src/tracking.rs:932-933`
- **Description**: The `RTK_TEE_DIR` and `RTK_DB_PATH` environment variables are used directly as file paths without validation. An attacker with environment variable control (shared systems, CI/CD, container escape) could redirect file writes to sensitive locations.
- **Impact**: Write to arbitrary filesystem locations (tee files), redirect database to attacker-controlled location. Limited by OS file permissions.
- **Recommendation**: Validate that paths are absolute, don't contain `..` segments, and target expected directories. Consider restricting to subdirectories of `~/.local/share/rtk/`.
- **Status**: Accepted Risk -- environment variable manipulation requires existing local access; OS permissions provide defense-in-depth.

#### FINDING-005: Unbounded Output Capture in Proxy Mode
- **Category**: CWE-400 (Uncontrolled Resource Consumption)
- **CVSS Estimate**: 3.7 (Low - requires user to run pathological command)
- **File**: `src/main.rs:1809-1843`
- **Description**: The proxy mode's stdout/stderr capture loops (`captured.extend_from_slice()`) have no upper bound on memory allocation. A command producing infinite or very large output (e.g., `rtk proxy cat /dev/urandom`) will consume unbounded memory until OOM.
- **Impact**: Process killed by OOM. In resource-constrained environments (containers, CI runners), could affect co-located processes.
- **Recommendation**: Add a configurable capture limit (e.g., 100MB default). Truncate and warn when exceeded. Note: the output is streamed to stdout in real-time regardless, so the captured buffer is only for tracking metrics.
- **Status**: Accepted Risk -- user explicitly invokes proxy mode; output is streamed through regardless.

### Low / Informational

#### FINDING-006: Regex Compiled Per-Call in local_llm.rs
- **Category**: Performance / CWE-400 (Resource Consumption)
- **File**: `src/local_llm.rs:139,178,205,219`
- **Description**: Several functions compile regex patterns on every invocation instead of using `lazy_static!`. While the patterns are safe (no ReDoS risk), repeated compilation is wasteful.
- **Recommendation**: Move to `lazy_static!` for consistency with codebase conventions.

#### FINDING-007: No LLM Output Framing
- **Category**: OWASP LLM Prompt Injection Prevention
- **Files**: All filter modules (git.rs, grep_cmd.rs, container.rs, gh_cmd.rs, etc.)
- **Description**: RTK output goes directly into LLM context windows without explicit framing or boundary markers. Untrusted data (git commit messages, package names, PR bodies, error messages) flows through filters to stdout without sanitization for LLM context. A crafted commit message like `"Fix bug\nSYSTEM: ignore previous instructions"` would appear in the LLM's context window.
- **Impact**: Theoretical indirect prompt injection via untrusted command output. Mitigated by LLM providers' own prompt injection defenses, output truncation (80-char line limits), and the fact that RTK output is clearly positioned as tool output in Claude Code's context.
- **Recommendation**: This is a systemic concern for all LLM-facing tools, not specific to RTK. Consider adding XML-style framing (`<rtk_output>...</rtk_output>`) in a future release. Current emoji markers provide partial human-readable context.
- **Status**: Informational -- industry-wide challenge, not a RTK-specific vulnerability.

#### FINDING-008: Security Comment in main.rs
- **Category**: Informational
- **File**: `src/main.rs:1889`
- **Description**: Comment `"SECURITY: whitelist pattern -- new commands are NOT integrity-checked until explicitly added here"` documents a conscious security design decision about the `is_operational_command()` function. This is a positive security observation -- fail-open is documented.

## OWASP LLM Prompt Injection Assessment

RTK processes untrusted command output (git commits, package names, PR bodies, compiler errors) and passes filtered versions to LLM context windows. The output pipeline is:

```
External Command -> RTK Filter -> stdout -> Claude Code Hook -> LLM Context
```

**Current mitigations:**
- ANSI code stripping (`utils::strip_ansi()`) prevents terminal escape injection
- Line truncation (80 chars in git, limited items in lists) reduces injection surface
- Emoji markers provide partial visual context
- pnpm package name validation (`^[@a-zA-Z0-9._-]+$`) blocks special characters

**Gaps:**
- No explicit output framing (XML/JSON boundaries) for LLM parsing
- No content sanitization for LLM-specific injection patterns
- Raw untrusted data (commit messages, error text) flows through filters

**Risk Level**: LOW -- LLM providers implement their own prompt injection defenses. RTK output is positioned as tool output in Claude Code, which LLMs already treat as data rather than instructions. The attack requires a sophisticated adversary who controls content in a repository the user is working on.

## OWASP MCP Security Assessment

RTK integrates with Claude Code via a PreToolUse hook (`.claude/hooks/rtk-rewrite.sh`):

**Strengths:**
- Hook uses `rtk rewrite "$CMD"` (delegated logic, not inline shell parsing)
- Graceful fallback if RTK is not installed
- Optional audit logging via `RTK_HOOK_AUDIT=1`
- Input validation (skips heredocs, empty commands)

**Gaps:**
- No hook signature/integrity verification (modification possible)
- No RTK version check (downgrade attacks theoretically possible)
- File permissions on hook not enforced

**Risk Level**: LOW -- hooks are part of the user's own repo/config. Claude Code's hook model already requires user approval.

## Positive Security Observations

1. **Parameterized SQL everywhere**: All SQLite queries use `params![]` macro -- zero SQL injection risk
2. **Safe command execution**: All operational commands use `Command::new().arg()` (not shell strings), preventing argument injection. Only `err`/`test`/`summary` use shell invocation (by design)
3. **No unsafe code**: Zero `unsafe` blocks in the entire `src/` directory
4. **Graceful error handling**: Consistent use of `anyhow::Result` with `.context()` -- no unwraps in production code paths
5. **Exit code preservation**: Commands properly propagate child process exit codes
6. **Input validation on package names**: pnpm module validates package names against `^[@a-zA-Z0-9._-]+$`
7. **Tee file rotation**: Bounded at 20 files / 1MB each (20MB max disk usage)
8. **No network surface**: RTK makes zero network requests -- no remote code execution or data exfiltration vectors
9. **ANSI stripping**: Multiple modules strip ANSI codes before output, preventing terminal escape attacks
10. **Documented security decisions**: `is_operational_command()` whitelist pattern is explicitly documented with security rationale
